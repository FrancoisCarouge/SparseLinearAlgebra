AGENTS.md

Guidance for coding agents working in this repository (the SparseLinearAlgebra library, git@github.com:FrancoisCarouge/SparseLinearAlgebra.git). This file is the repository root; all paths below are relative to it.

Human contributors: see CONTRIBUTING.md. AI coding agents: this file.

AI agent conduct

  • You are the author. Understand and be able to defend every line, however much a model wrote. A change nobody can explain is not ready.
  • This is a bleeding-edge C++26, concepts-and-templates, constant-evaluation codebase (the .clang-tidy Checks: '*' zero-NOLINT baseline described under Build & test assumes it). Every pattern computation runs in the compiler: models are weakest exactly here — watch for confident-but-wrong template metaprogramming, non-type template parameter deduction, and constant evaluation limits, and build and test the change yourself rather than trusting CI or the reviewer to catch it.
  • Propose before you build for anything touching the shape of the public API (pattern, sparse_matrix, its constructors and element accesses, an algorithm's signature or overload set), the structural zero model, or the pattern algebra's results: lay out the options and their consequences and get agreement first, rather than implementing one interpretation and letting the reviewer correct it. README's "Notes" and "Lessons Learned" record decisions already made — a structural zero has no reference, a write to it does not compile, a run-time position is read by value, a pattern is structural — read them before re-litigating one.
  • Keep diffs minimal. No unrequested reformatting, renaming, or opportunistic refactors riding along with an unrelated change. Run git status --short before touching anything, and stage named paths rather than git add -A/git add ..
  • Never commit in your own name. Every commit must be attributable to a human: its author and committer are the human contributor's own git identity (user.name/user.email), never an agent, model, or bot identity. Don't pass --author, set GIT_AUTHOR_*/GIT_COMMITTER_*, or edit the git config to name an AI, and don't add AI Co-Authored-By trailers; the human whose name is on the commit answers for it.
  • No publicity. Don't advertise the agent, model, or vendor anywhere in the project's history or contents: no "Generated with …" or "Written by …" footers, tool links, badges, emoji signatures, or other self-promotion in commit messages, PR/issue bodies, review comments, code comments, or documentation. Contributions speak for themselves, under the human contributor's name.
  • These two rules override your tool's defaults. Some agent harnesses instruct the model to append a Co-Authored-By trailer to commits or a "Generated with …" line to pull requests. This repository's rules take precedence: drop those lines from every commit message, PR body, and comment, and if one slips through, amend the commit and edit the body before review.

Build & test

The repository root is the CMake source directory. The canonical loop — the same one CI runs (.github/workflows/pipeline.yml) — is:

cmake -S . -B build -G Ninja
cmake --build build --parallel
ctest --test-dir build --parallel --verbose
  • Requires CMake ≥ 4.3 (cmake_minimum_required(VERSION "4.3")) and a C++26 compiler. Local builds use whatever cc/c++ resolve to on $PATH unless you pass -DCMAKE_CXX_COMPILER=; a distribution default such as GCC 13 is too old for C++26, so pass e.g. -DCMAKE_CXX_COMPILER=clang++-21. CI exercises clang++-20, clang++-21 (Ninja) and g++-14, g++-15 (Unix Makefiles) on ubuntu-26.04, MSVC cl (generator Visual Studio 18 2026, toolset pinned to 14.51 as in TypedLinearAlgebra and Kalman, because MSVC 19.52 fails to compile their mp-units dependency) on windows-2025 in both Debug and Release, and Apple Clang on macos-26.
  • The library has no dependency: include/ only includes the standard library. The benchmarks alone FetchContent nanobench, with SYSTEM, so the project's -Werror flags never apply to its headers. Keep it that way: a first or third party dependency belongs in a test, sample, or benchmark, never in a library header.
  • MSVC can't take CMAKE_CXX_STANDARD 26 (CMake doesn't record C++26 support for it, so requesting it hard-fails feature checks). support/support.cmake unset()s CMAKE_CXX_STANDARD under if(MSVC), and support/CMakeLists.txt's MSVC branch restores the dialect via /std:c++latest directly — the root CMakeLists.txt stays compiler-agnostic. Replicate that split rather than adding an if(compiler) branch at the root.
  • A release build defines NDEBUG, which removes the tests' assertions and leaves the variables they verify unused, an error under -Werror with GCC and Clang: the tests are built in debug, as CI's Linux jobs do, and only MSVC's Release job builds them in release. To measure the benchmarks in release, build their drivers only (see benchmark/README.md).
  • To run a single test, use CTest's -R/--tests-regex against the generated test name (see the naming convention below), e.g. ctest --test-dir build -R sparse_linear_algebra_multiplication_multiplication_pass --output-on-failure. The compile-time-only and compile-fail tests compile their file when CTest runs them, not during the build, so a compilation error in one surfaces as a test failure.
  • Formatting (enforced by .github/workflows/format.yml): clang-format-22 --Werror -i -style=file on .hpp/.tpp/.cpp, and cmakefmt (cmakefmt --check .; pipx install cmakefmt, upgrade with pipx upgrade cmakefmt) on every CMakeLists.txt/*.cmake/*.cmake.in. There is no .clang-format file in the repo, so -style=file falls back to clang-format's built-in LLVM style (80 columns, 2-space indent, template declarations always broken). Hand-written layout will not match it — always finish an edit by running clang-format-22 -i -style=file (that exact version; other versions disagree on wrapping) and cmakefmt --in-place <file> on every file you touched, and read the result: clang-format 22 mangles an immediately invoked lambda with a trailing return type whose template arguments name a member, such as [] -> pattern<Pattern.columns, Pattern.rows, Pattern.count> {...}(), into unbalanced code. Let such a lambda deduce its return type ([] {...}()), as sparse_linear_algebra::internal::projection does.
  • cmakefmt reads the repository-root .cmakefmt.yaml: 80 columns and 2-space indent (its defaults), command_case: unchanged so mixed-case module commands such as FetchContent_Declare keep their spelling, and a commands: section describing the project's own pass/build/fail (BACKENDS keyword), sample, bench, and amalgamate functions so their calls wrap keyword-aware. Declare any new project-level CMake function there too; cmakefmt --list-unknown-commands . must report none. Recursive discovery honours .gitignore, so build/ is skipped.
  • cmakefmt is deliberately unpinned: CI installs the latest release on every run and the pre-commit hook is a language: system hook calling whatever cmakefmt is on $PATH. Keep your local install current, or a newer release's layout changes will fail CI while passing locally.
  • .clang-tidy runs Checks: '*' with WarningsAsErrors: '*' (minus a short denylist) — a very strict baseline; don't casually suppress warnings. .github/workflows/clang_tidy.yml configures the build with clang++-20 (-DCMAKE_EXPORT_COMPILE_COMMANDS=ON), then run-clang-tidy -p build over every benchmark|sample|support|test/*.cpp except *_fail.cpp, sharded 6 ways. The codebase has no NOLINT, and the no-nolint pre-commit hook rejects any — rework the code instead. Gotchas:
    • misc-include-cleaner: every standard library symbol needs a direct include of its own header, even if transitively available. .clang-tidy's IgnoreHeaders whitelists only the library's own fcarouge/sparse_linear_algebra* headers, never the standard library.
    • misc-redundant-expression rejects a comparison of a value with itself, the usual not-a-number check value != value: verify a not-a-number value by its unordered comparisons instead, not(value < 0.) and not(value >= 0.), as test/square_root/ does.
    • google-readability-casting reports a C-style cast where a variable template's initializer names a non-type template parameter of an enumeration type, template <stored_by Storage> inline constexpr ... {... Storage ...}, a false positive of clang-tidy 21: select by the member of a structure, as sparse_linear_algebra::internal::stored_terms groups its positions, rather than by an enumeration template argument.
    • cppcoreguidelines-pro-bounds-constant-array-index rejects a run-time subscript in a test or a sample: use std::array::at, which a hosted test or sample may.
    • Run it before finishing: run-clang-tidy-21 -p build path/to/file.cpp from a -DCMAKE_EXPORT_COMPILE_COMMANDS=ON build. With the Ninja generator, first build the targets of the files to lint: their compile commands reference C++ module map (.modmap) files that only exist after a build; a build() or fail() target is only built by its test.
    • No HeaderFilterRegex is set, so clang-tidy reports nothing in include/ headers, in CI or locally. Forcing -header-filter='.*/include/fcarouge/sparse_linear_algebra.*' surfaces findings inherent to the design, which are accepted: a run-time subscript into a compile-time-sized std::array (cppcoreguidelines-pro-bounds-constant-array-index, the freestanding library has no at() that does not throw), public data members (misc-non-private-member-variables-in-classes, a structural type, usable as a template argument, has only public members), the deduced return type of an immediately invoked lambda (modernize-use-trailing-return-type, see the clang-format gotcha above), and the documentation re-declarations of the //! @name Algorithms block (readability-redundant-declaration). Read the remaining ones, and fix a new one.
  • CppCheck (.github/workflows/cppcheck.yml) builds CppCheck from its master branch and fails on any finding, its syntaxError included. It misparses some valid C++, which the code avoids rather than suppresses: a lambda as a template argument (sparse_matrix<double, pattern{shape<R, C>, [](...) {...}}>: name the predicate as a variable template, as sparse_linear_algebra::internal::every and sparse_linear_algebra::internal::within_band are), if consteval and if !consteval (use std::is_constant_evaluated()), a comparison of member accesses joined by && (i < Lhs.count && j < Rhs.count, read as a template argument list: parenthesize each comparison), a member access closing a template argument list (std::make_index_sequence<Pattern.rows>: name it as a variable template, as sparse_linear_algebra::internal::row_count is), a loop condition comparing to a member function call (i < value.values.size(): compare to a named constant), a braced pattern construction inside a matrix's template argument list (sparse_matrix<double, pattern{shape<2, 1>, {{1, 0}}}>, an internalError: name the pattern as a constant first, constexpr pattern column{shape<2, 1>, {{1, 0}}};), and an explicitly spelled pattern of no position (pattern<2, 2, 0>, a false containerOutOfBounds in the constructor from listed positions, whose constraint it ignores: spell the type from a constructed pattern, decltype(empty)). Its suppressions, each scoped to one file and one check, cover the deliberate raw loops of the algorithms (useStlAlgorithm: the freestanding library does not depend on the algorithms library), the implicit converting constructor (noExplicitConstructor), and its false functionStatic findings, for the sources and the amalgamated header alike. An assert constructing a temporary is an assertWithSideEffect finding: compare to a named constant.
  • Pre-commit hooks (.pre-commit-config.yaml, run in CI by .github/workflows/pre_commit.yml): pre-commit install once per clone installs both the pre-commit and commit-msg hook types; pre-commit run -a runs everything. Covers repository hygiene (LF line endings, whitespace, case/Windows-name conflicts, large files, merge markers), gitleaks, clang-format pinned to v22 and cmakefmt (the same checks as format.yml), codespell, workflow/Dependabot/CITATION.cff schema validation, actionlint (.github/actionlint.yaml declares the ubuntu-26.04 runner label), and local checks for the SPDX Unlicense header, NOLINT, and the [tag] description commit-message form. zizmor (GitHub Actions security audit) is not configured.
    • actionlint lints run: scripts with shellcheck only when shellcheck is on $PATH, and silently skips that check otherwise — CI has it, so install it locally (apt install shellcheck or pip install shellcheck-py) or a passing local run can still fail CI.
  • Sanitizers (.github/workflows/sanitizer.yml, sanitizer_memory.yml), Valgrind (valgrind_memory.yml), coverage, cppcheck, CodeQL, and Doxygen also gate pull requests. The coverage job (coverage.yml, GCC and lcov) fails below 100% of the lines and functions of include/, and lcov counts each template instantiation as a function of its own: a lambda inside an operation is instantiated for every pair of patterns, and is uncovered for a pair that never calls it, so an element operation is a variable template of the element type only, as sparse_linear_algebra::internal::sum is. A run-time path that a hosted test never reaches, such as the freestanding square root, needs a pass(... BACKENDS "freestanding") test. Doxygen warnings are reported in its job log without failing it (WARN_AS_ERROR = NO, as in TypedLinearAlgebra and Kalman): only a generation error fails the job. Coverity Scan (.github/workflows/coverity.yml) does not gate pull requests: it runs on a schedule or manually, to stay within the service's weekly submission limit and to keep its COVERITY_SCAN_TOKEN and COVERITY_SCAN_EMAIL secrets away from pull request code. To reproduce a sanitizer locally, export the job's CXXFLAGS/LDFLAGS and run-time *SAN_OPTIONS from the workflow matrix before configuring.
  • cmake --build build --target amalgamate generates the single-header build/amalgamate/fcarouge/sparse_linear_algebra.h from include/fcarouge/sparse_linear_algebra.hpp (support/amalgamate/); .github/workflows/deploy_amalgamate.yml publishes it, and test/amalgamate/ verifies it.
  • Install: sudo cmake --install build. test/install/ installs into a staging prefix and builds a consumer through find_package, so a header missing from the FILE_SET of include/CMakeLists.txt fails a test.

Architecture

Public headers

include/fcarouge/sparse_linear_algebra.hpp is the single public entry point. It includes the parts of the library, in dependency order, each a header of include/fcarouge/sparse_linear_algebra/, declares the sparse_matrix class and the literals::operator""_o structural zero literal, then includes the algorithms (algorithm/*.tpp, alphabetical), the hosted formatting (format.tpp), the literal definition (literals.tpp), and the member definitions of sparse_matrix (sparse_linear_algebra.tpp), as TypedLinearAlgebra and Kalman do, and redeclares the free functions and operators for documentation in its //! @name Algorithms block (the curated public API listing Doxygen renders; the @brief/@details/@see/@complexity live once, on the definition). The members of sparse_matrix are the other way around: documented once, on their declarations in the class, and defined undocumented in sparse_linear_algebra.tpp. A .tpp file is only included by sparse_linear_algebra.hpp, after the class declaration: it includes the forward declaration header, never the entry point. MSVC does not match an out-of-class member definition to its declaration when a template parameter of the class, or of the member template, is a constrained placeholder (sparsity_pattern auto Pattern): sparse_matrix and its member templates take an auto parameter constrained by a requires-clause (requires sparsity_pattern<decltype(Pattern)>), repeated verbatim on each definition. The free functions keep the constrained placeholder. include/fcarouge/sparse_linear_algebra_forward.hpp is the authoritative forward declaration header: it declares position, pattern, and sparse_matrix, and defines the sparsity_pattern concept the sparse_matrix declaration is constrained by, by deducing the arguments of a pattern. It declares nothing of the sparse_linear_algebra::internal namespace, and there is no namespace alias of it: the library and the tests spell it out.

  • pattern.hpp — position, absent, pattern (its constructors and deduction guides, lower_bound, index_of, stores, operator==), the shape_t tag and its shape value, and the named patterns dense, zero, banded, diagonal, tridiagonal, lower_triangular, upper_triangular.
  • pattern_algebra.hpp — the public pattern computations: pattern_union, pattern_intersection, pattern_transpose, pattern_product, product_term_count, structural_rank, pattern_quotient, is_subset_of, is_structurally_symmetric, pattern_cholesky.
  • sparse_linear_algebra.tpp — the member definitions of sparse_matrix, declared in sparse_linear_algebra.hpp.
  • algorithm/ — one .tpp per operation: add (+), divide (/ by a scalar, and by a matrix: the block triangular solution of x * rhs = lhs), dot, equal_to (==), matrix_frob_norm, matrix_inf_norm, matrix_one_norm, minus (unary -), product (* of matrices and by a scalar), subtract (binary -), transposed.
  • format.tpp — the std::formatter specialization, hosted only.
  • literals.tpp — the definition of the 0_o structural zero literal, declared in sparse_linear_algebra.hpp.
  • internal/utility.hpp — the pattern computations of the operations: position_list, to_pattern, merge_positions, term_count, product_positions, projection, term, stored_count, stored_terms, row_bounds, dot_terms, the structural analysis of a division (maximum_matching, block_triangular_form, quotient_reach, quotient_positions), the symbolic Cholesky factorization (cholesky_columns, cholesky_position_count, cholesky_positions), absolute, square_root, the is_matrix/element_t traits, and the construction from every row: the structural_zero type of the 0_o literal, row, and the storage base of sparse_matrix. internal/combine.hpp — the element-wise combination shared by + and binary -.

The compile-time pattern model

A pattern<Rows, Columns, Count> is a structural type, a valid non-type template argument, holding its stored positions in strictly ascending row-major order: equal patterns are one and the same sparse_matrix type, and a stored element's index in sparse_matrix::values is its rank among the positions. Its consteval constructors enforce that invariant, so it is not an aggregate and has no default constructor: the constructor from listed positions (insertion sort, linear on positions already in order, rejecting a duplicate or out-of-range position by calling the never-defined sparse_linear_algebra::internal::position_out_of_range_or_duplicate(), which ends the constant evaluation and names the defect in the diagnostic), the constructor from a stateless predicate (row-major by construction), and the one from the shape alone, of no position. Deduction guides deduce the count of stored elements, from the size of the listed positions or by evaluating the predicate's default-constructed type (sparse_linear_algebra::internal::count_of, a constrained function so that a non-predicate argument is a substitution failure). The listed positions constructor is a template on its own size, constrained to the count: an array of no position is not a type. The pattern algebra builds its results through the listed positions constructor too (sparse_linear_algebra::internal::to_pattern), from lists already in order, never by filling positions.

Each operation's result pattern is a variable template of the pattern algebra, and its arithmetic is a precomputed table: sparse_linear_algebra::internal::projection<From, To> maps the stored elements of one pattern into another, sparse_linear_algebra::internal::stored_terms<Lhs, Rhs, To> groups the positions of a pattern by the operands storing them, both, the left one only, or the right one only, for the element-wise operations, the equality, and the conversion, sparse_linear_algebra::internal::product_terms<Lhs, Rhs> (in product.tpp) lists every elementary product grouped by result element, and sparse_linear_algebra::internal::dot_terms the products of a dot product. At run time an operation only walks its table: no lookup, no branch on the pattern, no structural zero computed. An operation never branches at run time on absent before an access: GCC cannot prove such a guarded index in bounds, and warns -Warray-bounds on the unreachable read of values[absent] at -O3; walk a table of the positions each operand stores instead, and loop over the stored elements directly when both operands are of the same pattern, which the compilers vectorize. Likewise, an operation on a pattern without a structural zero computes its indexes, row-major, rather than read them from a table (transposed, matrix_one_norm), a row sum walks the contiguous stored elements of its row (matrix_inf_norm), and a division of at most sparse_linear_algebra::internal::division_constant_blocks blocks solves each block of its constant size and table ranges, an instantiation each, beyond which it loops over its blocks. The matrix and dot products expand their tables at compile time instead, each elementary product an expression of compile-time indexes, in fold expressions of at most sparse_linear_algebra::internal::fold_size products: a loop over a table of indexes loads them from memory and accumulates through them, which the compilers neither unroll nor keep in registers beyond a few dozen terms. The bound keeps each fold within Clang 20's expression nesting limit and the instantiations few: an instantiation per result element, each carrying both patterns, multiplies GCC's compile time on large patterns. Each expanded product is still an expression of its own, whose compile time and memory grow with the products: beyond sparse_linear_algebra::internal::unrolled_term_limit elementary products, where a loop catches up with the expanded products' run time, the matrix product accumulates a row of its result at a time instead (sparse_linear_algebra::internal::row_product), from the row bounds of the patterns only, in the same order of terms, so both compute the same values. Preserve that split when adding an operation: compute everything that depends on the patterns in a constexpr variable template or a consteval function, and keep the run-time work to the stored elements or terms only.

The compile-time cost is the constraint of this design. The pattern operations are near-linear in the stored elements and verified at 100 x 100 (test/scalability/patterns.cpp): the symbolic product unions rows of bits, rather than enumerating the elementary products, and the transposition sorts by column in a single pass. A product expanded at compile time precomputes each of its elementary products, which bounds it to sparse_linear_algebra::internal::unrolled_term_limit of them; a larger one accumulates by rows, and a 100 x 100 dense product is verified (test/scalability/large.cpp). Measure the constant evaluation cost of a new table on large patterns, and never raise the compilers' limits in the build to hide one.

The structural zero model

A structural zero has no storage, so it has nothing to refer to: no write may reach it, and no write may be lost. The element accesses of sparse_matrix encode it in their overloads, and every rejection is a compile error, detectable by a requires expression:

  • at<Row, Column>() returns a reference, constrained on Pattern.stores(Row, Column). The const overload, constrained on the position being in the matrix, reads any position by value, a structural zero as Type{}. For a structural zero of a modifiable matrix, overload resolution falls to that const overload, whose value an arithmetic element type cannot be assigned: value.at<0, 1>() = 1.; does not compile.
  • operator[](row, column) const reads a run-time position by value. The non-const reference overload exists only without a structural zero (Pattern.count == Pattern.rows * Pattern.columns), where the storage is an ordinary dense row-major array.
  • operator[](std::integral_constant<std::size_t, Row>, std::integral_constant<std::size_t, Column>) returns a reference to a stored element: the generic access of a linear algebra library by compile-time position, the type of TypedLinearAlgebra's _i literal, through which a typed facade writes an element of this storage. Its const overload, constrained on the position being in the matrix, reads any position by value, as at<Row, Column>() const does, through which a typed facade reads an element in constant time: an integral_constant also converts to a run-time position, so without it a compile-time read would silently fall to the run-time read and its logarithmic lookup. For a structural zero of a modifiable matrix, overload resolution falls to that const overload.
  • The constructor from stored elements takes exactly Pattern.count values of exactly Type; the constructor from every row, {{4., 0_o}, {0_o, 1.}}, takes a braced list per row, a value of exactly Type at each stored element and the 0_o literal at each structural zero, checked by constraints: it is inherited from the internal storage base, which holds values and whose row parameters expand the pattern's row indexes, one non-deduced row type each, which a braced list initializes; the conversion constructor, implicit (explicit(false)), only accepts a pattern whose positions this pattern all stores (is_subset_of).

A structural zero is also a property of the type, not a value: it is never multiplied, so 0 * infinity is never computed and a non-finite operand does not propagate through it (test/non_finite/). Document a new operation's behavior on non-finite values when it differs from a dense computation.

Algorithms

The algorithms are free functions and operators of namespace fcarouge, the namespace of sparse_matrix, found by argument-dependent lookup on it: a pattern is a non-type template argument, which brings no associated namespace, so an algorithm of fcarouge::sparse would not be found. They are [[nodiscard]] constexpr, returning by value. Their names and semantics mirror std::linalg (dot, matrix_frob_norm, matrix_inf_norm, matrix_one_norm, transposed; //! @see std::linalg::<name>), and the operators mirror mathematical notation. Their signatures deduce the element type and the patterns, template <typename Type, sparsity_pattern auto Lhs, sparsity_pattern auto Rhs> with const sparse_matrix<Type, Lhs> & parameters, and constrain the shapes in a requires clause, so a mismatch is a substitution failure, not a hard error. A scalar operand is const std::type_identity_t<Type> &, so that it does not take part in the deduction and converts to the element type. Operands of different element types do not mix, by design.

Each algorithm loops over the stored elements, never the positions, and uses no algorithm of the standard library: the raw loops keep the library freestanding. A floating-point only algorithm constrains its element type (std::floating_point Type), and computes its square root through sparse_linear_algebra::internal::square_root, which is std::sqrt at run time on a hosted implementation and Newton's method at compile time or freestanding.

Freestanding, real-time, and constant expressions

The library headers stay freestanding: no hosted-only standard header, no exception, no run-time type information, no memory allocation, no input-output. A hosted-only feature fences its own file content, includes included, under #if __STDC_HOSTED__ inside its include guard, as format.tpp does and internal/utility.hpp does for <cmath>, so the core header includes it unconditionally. Guard on __STDC_HOSTED__ or a feature-test macro, never on __has_include alone: a freestanding standard library ships its hosted-only headers too, which reject their inclusion. The freestanding backend target (support/freestanding/) compiles its dependents with -ffreestanding -fno-exceptions -fno-rtti on GCC and Clang (MSVC has no freestanding mode); libstdc++ then rejects a hosted-only header. test/freestanding/ holds its build()-only static_assert tests, and .github/workflows/freestanding.yml cross-compiles them, and the amalgamated header, for a bare-metal Arm Cortex-M4.

Every operation is constexpr, and tested as such (test/constexpr/, and the static_asserts of the build() tests). A run-time test therefore needs a run-time value, or the compiler evaluates its whole body as a constant initialization and never runs its assertions: a pass test whose body would otherwise be a constant expression starts with [[maybe_unused]] const volatile int run_time{0}; assert(run_time == 0);, whose volatile read is not a constant expression. A test that formats or prints is not one.

Every test, sample, and benchmark is real-time verified by default: built with -fsanitize=realtime (the Real-Time job of sanitizer.yml), the sparse_linear_algebra_realtime object in support/main (realtime.cpp, linked through sparse_linear_algebra_main, and directly by bench()) runs the whole program in a real-time context, as if its entry point were [[clang::nonblocking]], so a memory allocation, lock, or blocking input-output call aborts it. An entry point that genuinely cannot be real-time (it formats, prints, or benchmarks) opts out explicitly: #include "fcarouge/realtime.hpp" and declare const not_realtime opt_out; as the first statement of its test/sample lambda, or at namespace scope of a benchmark. Never opt out to silence a finding in code meant to be real-time. Without the sanitizer the token does nothing. support/main/ is kept identical to TypedLinearAlgebra's but for the SPDX header block: synchronize it by copying.

Relation to TypedLinearAlgebra and Kalman

The library stands on its own: it neither includes nor fetches TypedLinearAlgebra (TLA) nor Kalman. TLA is expected to adopt it as a backend, composing sparse_matrix beneath its typed_matrix with the unit support on its side, as prototyped in TLA's pull request #579. The integral_constant element access is the one convention designed for that composition; keep it, and keep the library free of any notion of element types, units, or indexes. A change that only TLA's integration needs is proposed first, never implemented speculatively.

The project shares TLA's and Kalman's conventions, tooling, and layout: .clang-tidy, .pre-commit-config.yaml, the workflows, documentation/ (Doxyfile, Doxygen Awesome theme), support/amalgamate/, and support/main/ are copies adapted only for the project names. When a convention changes in one of them, synchronize the others.

Test/sample/benchmark generation (support/support.cmake)

Tests are not hand-declared; CMake functions generate them from a file name and an optional BACKENDS list, the only backend being freestanding:

  • pass(NAME [BACKENDS ...]) — compiles NAME.cpp into an executable linking slinalg, sparse_linear_algebra_main, sparse_linear_algebra_options (the warnings-as-errors and hardening flags of support/CMakeLists.txt), and the backend target, and registers it with CTest as sparse_linear_algebra_[<backend>_]<dir>_<name>_pass, where <dir> is the calling directory's name.
  • build(NAME [BACKENDS ...]) — compile-time-only: an OBJECT library, EXCLUDE_FROM_ALL, with no main linked and nothing run; the CTest test builds the target. Use it for static_assert-only tests: patterns, result types, concepts, constant expressions. It shares the _pass test name suffix.
  • fail(NAME [BACKENDS ...]) — the same shape as build, but expects a compilation failure (WILL_FAIL TRUE), producing sparse_linear_algebra_[<backend>_]<dir>_<name>, where the file name ends in _fail.
  • sample(NAME) — the same shape as pass, producing sparse_linear_algebra_sample_<name>.
  • bench(NAME SIZE) — configures NAME.cpp into NAME_SIZE.cpp, replacing its ${SIZE} placeholder, and registers a nanobench benchmark sparse_linear_algebra_<dir>_<name>_<size>_bench, with interprocedural optimization when supported. Sizes other than the default one are only declared with -DBUILD_BENCHMARKING=ON.

The build targets append _driver (_build_driver for build()), so build a test with e.g. cmake --build build --target sparse_linear_algebra_dot_dot_pass_driver. The build and fail tests carry the sparse_linear_algebra_build_tree CTest RESOURCE_LOCK: each one invokes the build tool on the shared build tree, which is not safe to run concurrently with itself. Every executable is registered optionally wrapped by the COMMAND environment variable (how the Valgrind workflows inject valgrind).

test/ is organized one directory per operation, feature, or concept, each with its own CMakeLists.txt listing one build(...), fail(...), or pass(...) call per test file, in that order and alphabetical within each; test/CMakeLists.txt itself only add_subdirectorys them, alphabetically:

  • Patterns: pattern/ (construction, named patterns, the concept, and their rejections), pattern_algebra/ (the algebra and each operation's result pattern), scalability/ (the compile-time cost at the supported scale, and a large run-time matrix).
  • The matrix: assign/, at/ (element accesses, and each rejected write), constructor/, singleton/, storage/ (the layout: only the stored elements).
  • Operations: addition/, division/, dot/, equal_to/, matrix_frob_norm/, matrix_inf_norm/, matrix_one_norm/, minus/, multiplication/, scale/, subtraction/, transposed/, format/.
  • Cross-cutting verifications: constexpr/ (every operation in a constant expression), differential/ (every operation of pairs of patterns against textbook dense loops, at compile time and run time), non_finite/, operation_count/ (the exact count of elementary operations, through a counting element type), realtime/ (every operation in the real-time context), square_root/, freestanding/.
  • Packaging: amalgamate/ (the single header), install/ (a find_package consumer of the installed package).

Test files are minimal: #include "fcarouge/sparse_linear_algebra.hpp", then a single [[maybe_unused]] const auto test{[] -> int { ...; assert(...); return 0; }()}; block inside namespace fcarouge::test { namespace { ... } } with a //! @test one-liner on top — no test framework, just <cassert> run at static-initialization time via main from support/main. Wrap an assert argument containing a comma, a template argument list, in double parentheses: assert((value.at<0, 1>() == 2.));. Samples use the same shape in namespace fcarouge::sample, with a //! @example Doxygen block, and print their results.

A fail test keeps the valid form of the rejected line in an // Intended: comment directly above it, and holds a single rejected construct. WILL_FAIL accepts any compile error, so build each fail target once and read its diagnostic to confirm it fails for the intended reason, at the intended line, not for a typo or a missing include. A requires probe at namespace scope hard-errors instead of yielding false on substitution failure, since it is not in a template: wrap a negative probe in a test-local concept, as test/at/access.cpp does.

Prefer values exactly representable in binary floating point (halves, quarters, small integers) so a test asserts with ==, and pick operands for which each plausible wrong implementation gives a different answer: negative elements for an absolute value, a non-square matrix for a row and column mix-up, a row vector for a vector norm special case, patterns that overlap partially for a union or a product.

Recipe: adding an algorithm

  1. Proposal. Describe the operation, its result pattern, its arithmetic terms, and its behavior on structural zeros and non-finite values; agree on it first (see AI agent conduct).
  2. Pattern algebra. If the result pattern is new, add it as a public variable template of pattern_algebra.hpp, built by consteval helpers of internal/utility.hpp, with its @brief/@details and a README "Pattern Algebra" row.
  3. Header. Create include/fcarouge/sparse_linear_algebra/algorithm/<name>.tpp: verbatim Unlicense SPDX block, include guard FCAROUGE_SPARSE_LINEAR_ALGEBRA_ALGORITHM_<NAME>_TPP, namespace fcarouge, the names of fcarouge::sparse qualified, the direct includes of what it uses. When std::linalg has the operation, mirror its name and semantics, returning by value, and add //! @see std::linalg::<name>. Precompute its table in a variable template of namespace sparse_linear_algebra::internal, in the .tpp itself when only it uses it, in internal/ when several algorithms share it; refer to it as sparse_linear_algebra::internal::<name>.
  4. Signature. Deduce the element type and the patterns, template <typename Type, sparsity_pattern auto Pattern> with const sparse_matrix<Type, Pattern> & parameters, constrain the shapes in a requires clause, declare the result type explicitly (-> sparse_matrix<Type, pattern_<name><Lhs, Rhs>>), and document its @complexity.
  5. Wire into sparse_linear_algebra.hpp. Add the #include "sparse_linear_algebra/algorithm/<name>.tpp" line (alphabetical, with the rest) and a matching, undocumented re-declaration in the //! @name Algorithms block, identical to the definition's signature, constraints included: a different one declares a second, ambiguous overload. Also list the new .tpp in the FILE_SET of include/CMakeLists.txt, or it is not installed; test/install/ catches the omission.
  6. README. Add a row to the "Operations" table, with its result pattern and complexity.
  7. Tests. A new test/<name>/ directory with its own CMakeLists.txt (SPDX comment block, then build(...), fail(...), pass(...) lines) and an alphabetical add_subdirectory("<name>") in test/CMakeLists.txt: a pass test of values on overlapping, disjoint, empty, rectangular, and vector patterns; the result pattern in test/pattern_algebra/result_patterns.cpp; a fail test per rejected shape or type; the operation in test/constexpr/, test/freestanding/, test/realtime/, and test/differential/ when it has a dense reference; its exact operation count in test/operation_count/ when it computes elementary products.
  8. Verify. cmake --build build --parallel && ctest --test-dir build --parallel; single test: ctest --test-dir build -R sparse_linear_algebra_<name>_<file>_pass --output-on-failure. Keep clang-format-22 --Werror, clang-tidy '*', and CppCheck clean, and Doxygen warning-free.

Conventions

  • Header-only library: keep the public API under include/fcarouge/ (sparse_linear_algebra.hpp, sparse_linear_algebra_forward.hpp, and the headers of sparse_linear_algebra/): sparse_matrix, its algorithms, and the sparsity_pattern concept in namespace fcarouge, as TypedLinearAlgebra's typed_matrix and Kalman's kalman, the 0_o literal in namespace fcarouge::literals, as TypedLinearAlgebra's _i literal, the patterns and their algebra in namespace fcarouge::sparse.
  • Internal implementation details live in namespace fcarouge::sparse_linear_algebra::internal — the single internal namespace, mirroring the include/fcarouge/sparse_linear_algebra/internal/ directory, and excluded from Doxygen (EXCLUDE_SYMBOLS). Never introduce fcarouge::internal, fcarouge::sparse::internal, or any other parallel internal namespace. Refer to internal entities by their qualified name from fcarouge (sparse_linear_algebra::internal::projection<From, To>, sparse_linear_algebra::internal::square_root(value)): there is no namespace alias, which would be a public name. The forward header, the users' entry to the declarations, declares nothing internal.
  • Public documentation states the contract and its rationale, not the implementation: what the function means, what it accepts or rejects and why, its result pattern and complexity, never which internal table or helper computes it. Implementation notes belong on the internal helper itself or in a plain // comment at the code they explain.
  • The author writes precise, terminology-careful @note/@todo/@warning Doxygen comments explaining design rationale directly in headers — match that register when editing docs/comments rather than simplifying. The vocabulary is fixed: a pattern stores positions; a matrix has stored elements and structural zeros; a product has elementary products or terms.
  • Every source/CMake file carries the Unlicense SPDX header block — copy it verbatim (version/URL match the root CMakeLists.txt) into any new file.
  • Consumers find_package the fcarouge-sparse-linear-algebra package and link against its namespaced fcarouge-sparse-linear-algebra::slinalg target (see INSTALL.md).
  • Blank lines separate groups of statements, not individual statements: includes of the same origin; using-declarations and type aliases; constant declarations; the construction of related objects; a run of assignments; a run of checks.
  • Uniform initialization, also known as brace initialization, is used as much as possible, in the library, its support, tests, samples, benchmarks, and documentation alike: braces read the same for every kind of initialization, reject narrowing conversions, and are never parsed as a function declaration. Brace a variable or constant (const auto value{expression};, for (std::size_t i{0}; ...)), a structured binding (const auto [row, column]{position};), a constructor member initializer, a default member initializer, a variable template definition, and an explicitly typed temporary (sparse_matrix<double, diagonal<2>>{1., 2.}). A default-constructed object whose type initializes itself stays default-initialized, without braces: a sparse_matrix (sparse_matrix<double, diagonal<3>> value;, zero-initialized), a not_realtime token. Write T value{}; only where default-initialization would leave a value indeterminate. A conversion that may narrow or promote is a named static_cast: braces reject it, and an implicit one warns. A function call or a named cast is not an initialization and keeps its parentheses.
  • An unused function parameter keeps its name in the signature, never commented out as /*name*/, and the body discards it with static_cast<void>(name); as its first group of statements: the name documents the parameter where the API is read, and the cast states the decision not to use it. A declaration without a body names the parameter too. Where the name would redeclare a local, rename the local rather than the parameter.
  • Class members follow the conventional order, as far as the language allows, so that a reader meets the interface before the implementation: the public section first, with its nested types, type aliases, and constants, then its constructors, assignment operators, and destructor, then its member functions; the protected section next, with the functions and hooks intended for derived classes; the private section last, with its helper member functions, then its static and non-static data members, ordered for their initialization dependencies or memory alignment. A data member that must stay public opens the public section with the types and constants, as the stored values of sparse_matrix do, next to its structure. A declaration sees only the names declared above it, whereas a member function body sees the whole class: a member type that a public signature or constraint names is itself public and first, and the private members a body uses stay last.
  • Commit messages follow [tag] short imperative description — a lowercase bracketed tag naming the area touched ([pattern], [matrix], [algorithm], [test], [sample], [benchmark], [cicd], [cmake], [documentation], [support], ...; git log --oneline has the established vocabulary). Match it rather than inventing Category: ... or type(scope): styles; the commit-message-tag hook enforces it.
  • PR/issue bodies and other GitHub-rendered Markdown use hard line breaks — a newline in the middle of a paragraph renders as <br>, so wrapped prose arrives as a ragged column. Write one paragraph per line there.
  • Keep PR descriptions concise: what changes and why, in a sentence or a short paragraph. Don't restate the diff, list the files touched, or add summary, test plan, or checklist sections: the diff and CI already show them.
  • No one-letter lowercase locals or parameters in test/sample code: name a value after its role (lhs/rhs for a binary operation's two sides, band, diffusion), which also keeps a future unit library's single-letter symbols (m, s) unshadowed when TypedLinearAlgebra composes these tests' patterns.
  • No _t suffix on the types test/sample code declares: name a type after its domain (band_matrix, stencil, transition), not its role with a suffix.
